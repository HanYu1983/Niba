# 條件邏輯設計（進入點綁定）

[← 上一篇：輸入資料模型](input-model.md) · [回到索引](../../../../project1/docs/SYSTEM_DESIGN.md) · [下一篇：結果 JSON →](result-json.md)

## 一進入點、一組條件

- 每個可執行進入點在建置時綁定**一組**條件實作（不同進入點 = 不同列表策略或不同條件組合）。
- 同一次行程中，資料夾內無論幾個 JSON，**皆使用同一組條件**評估合併後的列集合（合併規則見 [輸入資料模型 — 多檔合併](input-model.md#folder-merge)）。

## 評估上下文（建議欄位）

除既有 `RunId` 等外，應包含：

| 欄位 | 說明 |
|------|------|
| 列層級 `startDate` / `endDate` | 來自該列所屬輸入檔之外層。 |
| 輸入檔名 | 供日誌與結果 `sourceFile`。 |
| 批次基準時間 | 例如執行開始的 UTC 時間，供條件與有效期比較。 |
| `adName`（列上） | 對應階層名稱（`accName.capName.grpName.adName`），主要用於稽核／除錯與結果回填。 |
| `area`（列上） | 地區路由鍵；當需要呼叫某平台 API 時，應從此取得該 API 所需的地區／region 代碼（透過共用路由專案）。 |
| `platform` / `credentialCustomId`（來源檔外層） | 輸入 JSON 置於封套外層；合併後評估每一列時，應將該列**來源檔**外層之兩欄注入列上下文（等同與輸入一致），供條件內解析憑證並呼叫平台查詢 API。 |
| 憑證解析器／平台用戶端（可選） | 由進入點在 composition root 注入**憑證管理**與**平台共用專案**實例，避免條件內硬編秘密。 |

條件可為 `Async`，以便逐步加入各種 API。

## 單列決策（邏輯輸出）

| 欄位 | 說明 |
|------|------|
| `adId` | 與輸入一致 |
| `adName` | 與輸入一致（供結果 JSON 回填） |
| `platform` | 與輸入一致 |
| `credentialCustomId` | **必須**與輸入一致並寫入結果 JSON，供下游解析與查詢端相同的憑證。 |
| `desiredState` | `On` \| `Off` |
| `reason` | 可選；稽核用 |

（若需「不變更」可另擴充三態或由下游忽略該列。）

## 規則組合

- 在進入點專案內組合多條規則為單一條件集合；不強制放入共用核心庫。
- 未命中規則時的**預設 `desiredState`** 應在該進入點內明文定義並有測試。
